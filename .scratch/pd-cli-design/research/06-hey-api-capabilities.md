## 1. The seam: how every HTTP call is forced through one module

### 1.1 What the generator actually emits

With the fetch client plugin, `output/client.gen.ts` is a **three-line module** holding one
module-level client instance. Verbatim from the empirical run (`out_v2/client.gen.ts`):

```ts
// This file is auto-generated by @hey-api/openapi-ts

import { createClientConfig } from '../runtime.ts';

import { type Client, type ClientOptions, type Config, createClient, createConfig } from './client';
import type { ClientOptions as ClientOptions2 } from './types.gen';

export type CreateClientConfig<T extends ClientOptions = ClientOptions2> =
  (override?: Config<ClientOptions & T>) => Config<Required<ClientOptions> & T>;

export const client: Client = createClient(
  createClientConfig(createConfig<ClientOptions2>({ baseUrl: 'https://api.pipedrive.com/api/v2' }))
);
```

Note the `baseUrl` was picked up from the spec's `servers` entry automatically.

And `out_v2/sdk.gen.ts` (default `sdk.client: true`):

```ts
import { client } from './client.gen';

export const getDeals = <ThrowOnError extends boolean = false>(
  options?: Options<GetDealsData, ThrowOnError>
): RequestResult<GetDealsResponses, unknown, ThrowOnError> =>
  (options?.client ?? client).get<GetDealsResponses, unknown, ThrowOnError>({
    responseValidator: async (data) => await zGetDealsResponse.parseAsync(data),
    security: [{ name: 'x-api-token', type: 'apiKey' }, { scheme: 'bearer', type: 'http' }],
    url: '/deals',
    ...options
  });
```

`(options?.client ?? client)` is the whole story: there is a default client, and callers *may*
substitute their own per call.

Source: docs <https://heyapi.dev/docs/openapi/typescript/clients/fetch>,
<https://heyapi.dev/docs/openapi/typescript/plugins/sdk>; empirical `out_v2/client.gen.ts`,
`out_v2/sdk.gen.ts`.

### 1.2 The strong seam — `sdk.client: false` (recommended)

`sdk.client` is documented in the installed types
(`node_modules/@hey-api/openapi-ts/dist/index.d.mts:4096-4107`):

> *"Use an internal client instance to send HTTP requests? This is useful if you don't want to
> manually pass the client to each SDK function. […] `@default true`"*

Setting it to `false` **removes the default client entirely from the SDK**. Verified: regenerating
with `{ name: '@hey-api/sdk', client: false }` produced an `out_ro/sdk.gen.ts` with
**zero imports from `./client.gen`** (`grep -c "from './client.gen'" → 0`) and this signature:

```ts
export type Options<TData extends TDataShape = TDataShape, ThrowOnError extends boolean = boolean, TResponse = unknown> =
  Options2<TData, ThrowOnError, TResponse> & {
    client: Client;   // <- REQUIRED, not `client?: Client`
    meta?: ...;
  };

export const getDeals = <ThrowOnError extends boolean = false>(
  options: Options<GetDealsData, ThrowOnError>          // <- `options` no longer optional
): RequestResult<GetDealsResponses, unknown, ThrowOnError> =>
  options.client.get<GetDealsResponses, unknown, ThrowOnError>({ ... });
```

**This is the answer to the decisive question.** With `sdk.client: false`, `strict: true` makes it a
*compile error* to call any generated operation without handing it a client. There is no ambient
client to fall back on. The hand-written module is the only thing that constructs a `Client`, so
the type system — not a convention — enforces the single choke point.

Trade-off: every call site inside the wrapper must pass `{ client }`. That is exactly one module,
so the cost is trivial.

### 1.3 The choke point inside the client: custom `fetch`

`Config.fetch` from `@hey-api/client-fetch@0.13.1` `dist/index.d.ts:160-166`:

```ts
/**
 * Fetch API implementation. You can use this option to provide a custom
 * fetch instance.
 *
 * @default globalThis.fetch
 */
fetch?: (request: Request) => ReturnType<typeof fetch>;
```

The generated client calls it once per request (`out_v2/client/client.gen.ts:99-101`):

```ts
const _fetch = opts.fetch!;
response = await _fetch(request);
```

This — not the interceptors — is where rate limiting, retry, concurrency limiting and budget
accounting belong, because it wraps the *whole* exchange and can call `_fetch` zero, one or many
times. Interceptors cannot retry; they only transform on the way in and out.

Order inside `request()` (`out_v2/client/client.gen.ts:91-107`):
`request interceptors → opts.fetch(request) → response interceptors`.

Interceptor API (`@hey-api/client-fetch` `dist/index.d.ts:134-151`) — `request`, `response` and
`error` middleware, each with `.use(fn)` / `.eject(id)`:

```ts
type ReqInterceptor<Req, Options> = (request: Req, options: Options) => Req | Promise<Req>;
type ResInterceptor<Res, Req, Options> = (response: Res, request: Req, options: Options) => Res | Promise<Res>;
type ErrInterceptor<Err, Res, Req, Options> = (error: Err, response: Res, request: Req, options: Options) => Err | Promise<Err>;
```

Use interceptors for cross-cutting *observation* (stderr logging, reading `x-ratelimit-*` and
`x-daily-requests-left` headers into the budget accountant). Use `fetch` for *control*.

### 1.4 `runtimeConfigPath` — config that survives regeneration

The client plugin accepts `runtimeConfigPath`, and the generated `client.gen.ts` imports from it
at module load (see 1.1). Docs: <https://heyapi.dev/docs/openapi/typescript/clients/fetch>.

```ts
// openapi-ts.config.ts
plugins: [
  { name: '@hey-api/client-fetch', runtimeConfigPath: './src/lib/pipedrive/runtime.ts' },
  ...
]
```

```ts
// src/lib/pipedrive/runtime.ts  — hand-written, never regenerated
import type { CreateClientConfig } from './v2/generated/client.gen';
import { guardedFetch } from './http-gate';

export const createClientConfig: CreateClientConfig = (config) => ({
  ...config,
  fetch: guardedFetch,          // rate limit + retry + p-limit + budget live here
  throwOnError: false,          // errors as values (default, stated explicitly)
  responseStyle: 'fields',      // { data, error, request, response } (default)
});
```

Note: `runtimeConfigPath` is only useful **with** the default client (`sdk.client: true`). If you
take the strong seam (`sdk.client: false`), you construct the client yourself and
`runtimeConfigPath` becomes redundant — keep the config in the wrapper module instead:

```ts
// src/lib/pipedrive/client.ts — the ONE module
import { createClient, createConfig } from './v2/generated/client';

export const pipedrive = createClient(createConfig({
  baseUrl: 'https://api.pipedrive.com/api/v2',
  fetch: guardedFetch,
  throwOnError: false,
}));
```

### 1.5 Honest limits of the seam

- `RequestOptions extends Config`, so `fetch`, `baseUrl` and `throwOnError` are **also accepted
  per call**. A call site inside the wrapper could pass its own `fetch:` and bypass the gate.
- `...options` is spread **after** `responseValidator` and `url` in every generated function, so a
  caller can override the response validator or even the URL.
- Both are only reachable from inside the wrapper module if `sdk.client: false` is used, since
  nothing outside can obtain a `Client`. Belt and braces: an ESLint `no-restricted-imports` rule
  banning imports of `**/generated/**` outside `src/lib/pipedrive/**`.

## 2. The zod plugin

### 2.1 What it emits

Plugin config `{ name: 'zod', definitions: true, requests: true, responses: true }` produced a
single `out_v2/zod.gen.ts` with **389 exported schemas** for the Pipedrive v2 spec. Naming
observed:

| Layer | Emitted name | Enabled by |
| --- | --- | --- |
| Reusable components | `zActivityItem`, `zFoo` | `definitions: true` |
| Query parameters | `zGetDealsQuery` | `requests: true` |
| Path parameters | `zGetDealPath` | `requests: true` |
| Headers | `zDeletePetHeaders` | `requests: true` |
| **Responses** | `zGetDealsResponse` | `responses: true` |

**Yes — responses are covered, and that is what matters here.** Docs:
<https://heyapi.dev/docs/openapi/typescript/plugins/zod/v4> — *"You can enable schema generation
for responses by setting `responses: true`."* One schema per operation; if the operation declares
several success responses, it becomes a `z.union([...])`
(<https://heyapi.dev/docs/openapi/typescript/plugins/zod/mini>).

Other documented options: `compatibilityVersion` (`3` | `4` | `'mini'`), `metadata`, `dates`,
`case`, `.name` templates per layer, and `types.infer` to emit `z.infer` aliases:

```js
{
  name: 'zod',
  compatibilityVersion: 4,
  responses: { types: { infer: true } },  // export type ResponseZodType = z.infer<typeof zResponse>
}
```

### 2.2 Fidelity — good, but only as good as the spec

The emitted schema is a faithful mechanical translation. Verbatim `out_v2/zod.gen.ts:759`:

```ts
export const zGetDealsResponse = z.object({
    success: z.boolean()
}).and(z.object({
    data: z.array(z.object({
        id: z.int(),
        title: z.string(),
        owner_id: z.int(),
        person_id: z.int(),          // <- spec says non-nullable; Pipedrive returns null
        org_id: z.int(),             // <- same
        value: z.number(),
        currency: z.string(),
        probability: z.number().nullable(),
        lost_reason: z.string().nullable(),
        expected_close_date: z.iso.date(),
        custom_fields: z.record(z.string(), z.unknown()),
        // ...
    })),
    additional_data: z.object({
        next_cursor: z.string()      // <- required, non-nullable. Last page returns null.
    })
}));
```

`allOf` becomes `.and(...)` (a `ZodIntersection`), which is worth knowing: intersections do not
support `.partial()`, `.pick()` or `.omit()`, so post-hoc relaxation of a generated response
schema in hand-written code is awkward. Fix the input, not the output.

### 2.3 Overriding a wrong schema, regeneration-safe: `parser.patch`

`parser.patch` mutates the **input spec** before the IR is built, so every plugin (types, zod, sdk)
sees the corrected shape and nothing in `generated/` is hand-edited. Documented at
<https://heyapi.dev/docs/openapi/typescript/configuration/parser>; the type
(`@hey-api/shared/dist/index.d.mts:1686-1862`) accepts either a whole-spec function or keys:
`input`, `meta`, `operations` (by `"METHOD /path"`), `parameters`, `requestBodies`, `responses`,
`schemas` (by name, or one function for all), `version`.

Documented per-schema form:

```js
parser: {
  patch: {
    schemas: {
      Foo: (schema) => {
        delete schema.properties.updatedAt.format;
        schema.properties.updatedAt.type = 'number';
      },
    },
  },
}
```

**Empirically verified** on the real Pipedrive spec — a whole-spec patch that sets
`nullable: true` on the three fields above:

```js
const relax = (node) => {
  if (!node || typeof node !== 'object') return;
  if (Array.isArray(node)) return node.forEach(relax);
  if (node.type === 'object' && node.properties) {
    for (const [k, v] of Object.entries(node.properties)) {
      if (['next_cursor', 'person_id', 'org_id'].includes(k) && v && typeof v === 'object') {
        v.nullable = true;     // OpenAPI 3.0 spelling — see caveat below
      }
    }
  }
  for (const v of Object.values(node)) relax(v);
};

export default {
  input: 'https://developers.pipedrive.com/docs/api/v1/openapi-v2.yaml',
  output: 'src/lib/pipedrive/v2/generated',
  parser: {
    patch: { input: (spec) => { relax(spec.paths); relax(spec.components); } },
    transforms: { propertiesRequiredByDefault: true },
  },
  // ...
};
```

Regenerated result (`out_patched/zod.gen.ts`):

```ts
person_id: z.int().nullable(),
org_id: z.int().nullable(),
next_cursor: z.string().nullable()
```

Caveat learned the hard way: Pipedrive's spec is **OpenAPI 3.0**, where nullability is
`nullable: true`, *not* a `type: [..., 'null']` array. A first attempt that appended `'null'` to
`type` degraded the schemas to `z.unknown().nullable()` — the base type was silently lost. Use the
3.0 spelling.

### 2.4 Wiring zod into the SDK — and why you probably should not

`sdk.validator` accepts `true | 'zod' | 'valibot' | { request, response }`
(`dist/index.d.mts:4176-4213`). With `{ response: 'zod' }` every generated function gets
`responseValidator: async (data) => await zGetDealsResponse.parseAsync(data)`, invoked at
`out_v2/client/client.gen.ts:171-174`.

A `ZodError` there is caught by the same `try/catch` that handles HTTP errors and is returned in
the `error` field (see §3), so it does not throw — but it is **indistinguishable from an HTTP
error** at the type level. Given §5, turning `sdk.validator.response` on with
`propertiesRequiredByDefault: true` and an unpatched spec will fail on real Pipedrive traffic.

Recommendation: leave `sdk.validator` **off**, and run the generated `z*Response` schemas
explicitly inside the wrapper module with `safeParse`, so the parse outcome maps to its own
neverthrow error variant.

## 3. Errors and non-2xx — how it composes with `neverthrow`

`RequestResult` (`@hey-api/client-fetch` `dist/index.d.ts:214-227`), with the default
`throwOnError: false` and `responseStyle: 'fields'`:

```ts
Promise<
  (
    | { data: TData extends Record<string, unknown> ? TData[keyof TData] : TData; error: undefined }
    | { data: undefined; error: TError extends Record<string, unknown> ? TError[keyof TError] : TError }
  ) & { request: Request; response: Response }
>
```

A **discriminated union returned as a value**. Nothing throws. This is close to ideal for
neverthrow.

Runtime behaviour, verbatim from the generated client (`out_v2/client/client.gen.ts:187-222`):

```ts
      const textError = await response.text();
      let jsonError: unknown;
      try { jsonError = JSON.parse(textError); } catch { /* noop */ }
      throw jsonError ?? textError;
    } catch (error) {
      let finalError = error;
      for (const fn of interceptors.error.fns) { /* ... */ }
      finalError = finalError || {};
      if (throwOnError) { throw finalError; }
      return responseStyle === 'data' ? undefined : { error: finalError, request, response };
    }
```

Three consequences the wrapper must handle:

1. **Non-2xx** → body parsed as JSON where possible, surfaced as `error`. `response` is present
   and `response.ok === false`, so `response.status` is available for the 429 / 401 / 403 / 404
   split.
2. **Transport failures** (DNS, TCP, abort) → the `fetch` call rejects, is caught by the same
   `catch`, and appears in the *same* `error` field with `response === undefined`.
3. **Response validation failures** → a `ZodError` in the *same* `error` field, but with
   `response.ok === true`.

So `error` is a union of three unrelated things, typed `unknown` for most operations. Classifier
for the wrapper:

```ts
type PdError =
  | { kind: 'transport'; cause: unknown }
  | { kind: 'http'; status: number; body: unknown }
  | { kind: 'validation'; issues: z.ZodError }
  | { kind: 'budget-exhausted' };

const classify = (r: { error: unknown; response?: Response }): PdError =>
  r.response === undefined         ? { kind: 'transport', cause: r.error }
  : !r.response.ok                 ? { kind: 'http', status: r.response.status, body: r.error }
  : { kind: 'validation', issues: r.error as z.ZodError };
```

Bridging to neverthrow — do **not** use `fromPromise` (the promise never rejects with
`throwOnError: false`); map the union:

```ts
import { ResultAsync, ok, err } from 'neverthrow';
import { getDeals } from './v2/generated/sdk.gen';

export const listDeals = (query: GetDealsData['query']): ResultAsync<Deal[], PdError> =>
  ResultAsync.fromSafePromise(getDeals({ client: pipedrive, query }))
    .andThen((r) => (r.error !== undefined ? err(classify(r)) : ok(r.data)));
```

Typed error shapes: where the spec declares non-2xx responses, the generator emits them, e.g.
`out_v2/types.gen.ts:6451`:

```ts
export type GetDealConversionStatusErrors = {
    404: { success: boolean; error: string; /* ... */ };
};
export type GetDealConversionStatusError = GetDealConversionStatusErrors[keyof GetDealConversionStatusErrors];
```

But the Pipedrive v2 spec declares almost none: `getDeals` is generated as
`RequestResult<GetDealsResponses, unknown, ThrowOnError>` — the error type parameter is literally
`unknown`. **Do not expect typed Pipedrive errors.** Validate the error body in the wrapper with a
hand-written zod schema for Pipedrive's `{ success: false, error, error_info }` envelope, or patch
the spec to declare a shared error response.

Also note `responseStyle: 'data'` collapses the result to `TData | undefined` and discards the
error entirely — never use it here.

## 4. Restricting generation to a read-only surface

`parser.filters.operations.include` / `.exclude` take exact `"METHOD /path"` keys *or* regular
expressions written as strings delimited by `/`. `exclude` wins over `include`. Docs:
<https://heyapi.dev/docs/openapi/typescript/configuration/parser>.

**Empirically verified against the real spec:**

```js
parser: {
  filters: { operations: { include: ['/^GET /'] } },
}
```

Result in `out_ro/sdk.gen.ts`:

```
grep -c "\.post<\|\.put<\|\.delete<\|\.patch<"  →  0
grep -c "\.get<"                                →  66
```

Zero write operations exist in the generated output. This makes the map's read-only safety
property structural rather than a runtime guard: an agent cannot call `addDeal` because
`addDeal` was never generated. Combine with `filters.orphans: false` (the default once any other
filter is set) to drop now-unreferenced schemas.

Two further layers worth stacking on top, since defence in depth is cheap here:
a request interceptor that throws on `request.method !== 'GET'`, and a Pipedrive API token scoped
read-only.

## 5. `propertiesRequiredByDefault: true` — what it does and its risk

JSDoc, verbatim from `@hey-api/shared@0.99.x` `dist/index.d.mts:1955-1967`:

> *"By default, any object schema with a missing `required` keyword is interpreted as 'no
> properties are required.' This is the correct behavior according to the OpenAPI standard.
> However, some specifications interpret a missing `required` keyword as 'all properties should be
> required.' This option allows you to change the default behavior so that properties are required
> by default unless explicitly marked as optional. `@default false`"*

Docs: <https://heyapi.dev/docs/openapi/typescript/configuration/parser>.

**It does not touch nullability.** `required` and `nullable` are orthogonal in OpenAPI: the flag
flips *presence*, never *null-acceptance*. So a field the spec lists without `nullable: true`
stays `z.int()` — and Pipedrive returning `null` fails the parse.

Why the flag is nonetheless right for Pipedrive: the v2 spec declares almost no `required` arrays.
With the flag `false`, essentially every field in `types.gen.ts` becomes optional, and downstream
code drowns in `?.` and `undefined` on fields that are in fact always present. The flag buys
usable types.

**The risk, made concrete.** From the actual generated output (§2.2):

- `person_id: z.int()` / `org_id: z.int()` — Pipedrive returns `null` for a deal with no linked
  person or organisation. Extremely common.
- `additional_data.next_cursor: z.string()`, required — Pipedrive returns `null` on the **last
  page** of a cursor paginated list. This is the map's locked "pagination is complete and correct
  by default" decision walking straight into a validation failure on the final page of every list
  command.
- `won_time` / `lost_time: z.string()` required — absent on an open deal.
- `close_time: z.string().nullable()` — the spec *does* mark some fields nullable, so the gaps are
  arbitrary rather than systematic. You cannot reason about which fields are safe; you have to
  observe real responses.

Mitigation, in order of preference:

1. Keep `propertiesRequiredByDefault: true` for good types, keep `sdk.validator` **off**, and
   validate in the wrapper with `safeParse` — a validation failure becomes a typed error, not a
   crash, and can be logged to stderr while still returning data (see open questions).
2. Correct the spec with `parser.patch` as fields are discovered wrong (§2.3). Regeneration-safe,
   reviewable in git, and improves types *and* schemas together.
3. Record real Pipedrive responses in a fixture-capture prototype and drive the patch list from
   observed nulls, not from guesswork.

Do **not** relax by hand-editing `zod.gen.ts` — regeneration clobbers it, and the `allOf` →
`.and()` intersections make programmatic relaxation of the generated schema awkward anyway.

## 6. Two specs (v1 and v2) in one project

Non-issue. `openapi-ts.config.ts` accepts an array of jobs, each with its own output directory;
separate directories mean separate module namespaces, so identical exported names (`getDeals`
exists in both specs) never collide. Docs:
<https://heyapi.dev/docs/openapi/typescript/configuration> — *"Throughout this documentation, we
generally reference single job configurations. However, you can easily run multiple jobs by
providing an array of configuration objects."* (Page fetched and verified; it also documents the
job matrix and the merge form quoted below.)

```ts
// openapi-ts.config.ts
import { defineConfig } from '@hey-api/openapi-ts';

const shared = {
  parser: {
    transforms: { propertiesRequiredByDefault: true },
    filters: { operations: { include: ['/^GET /'] } },
  },
  plugins: [
    { name: '@hey-api/client-fetch' },
    { name: '@hey-api/sdk', client: false },   // no ambient client anywhere
    { name: 'zod', responses: true },
  ],
};

export default [
  { ...shared, input: 'https://developers.pipedrive.com/docs/api/v1/openapi-v2.yaml',
    output: 'src/lib/pipedrive/v2/generated' },
  { ...shared, input: 'https://developers.pipedrive.com/docs/api/v1/openapi.yaml',
    output: 'src/lib/pipedrive/v1/generated' },
];
```

Consumed as:

```ts
import * as v2 from './v2/generated/sdk.gen';
import * as v1 from './v1/generated/sdk.gen';

await v2.getDeals({ client: pipedriveV2 });
await v1.getGoals({ client: pipedriveV1 });   // v1-only resource
```

Two things follow for the design:

- The two jobs produce **two `Client` instances** with different `baseUrl`s
  (`/api/v2` vs `/api/v1`). Both must be created by the one wrapper module and both must be given
  the same `guardedFetch`. Rate limit state, `p-limit` limiter and budget counter are **per
  account, not per client**, so they live in the gate module and are shared by both.
- Do **not** use the merge form (`input: [a, b], output: 'one-dir'`). Merging two specs that both
  define `Deal` and `getDeals` is exactly the collision to avoid.

Also documented: a job matrix (`input: [...], output: [...]` of matching length) — same effect as
an array of jobs, less explicit; and `output.case` if the v1 spec's naming needs normalising.

## 7. Recommended configuration for `pd`

```ts
// openapi-ts.config.ts
export default [
  {
    input: 'https://developers.pipedrive.com/docs/api/v1/openapi-v2.yaml',
    output: 'src/lib/pipedrive/v2/generated',
    parser: {
      patch: { input: patchPipedriveSpec },        // hand-written, grows as nulls are found
      transforms: { propertiesRequiredByDefault: true },
      filters: { operations: { include: ['/^GET /'] } },
    },
    plugins: [
      { name: '@hey-api/client-fetch' },
      { name: '@hey-api/sdk', client: false, validator: false },
      { name: 'zod', compatibilityVersion: 4, responses: true, requests: true },
    ],
  },
  /* v1 job, same shape */
];
```

Rationale in one line each:

| Setting | Why |
| --- | --- |
| `sdk.client: false` | Compile-time single choke point. The core requirement. |
| `sdk.validator: false` | Validation belongs in the wrapper where its failure becomes a typed error. |
| `zod.responses: true` | Response schemas are what the boundary needs. |
| `filters.operations.include: ['/^GET /']` | Write operations do not exist in the output. |
| `parser.patch` | Regeneration-safe spec corrections. |
| `propertiesRequiredByDefault: true` | Usable types; paired with patch + wrapper-side `safeParse`. |
| pin `typescript@^5` | TS 7 breaks the generator outright. |
| pin `@hey-api/openapi-ts` exactly | The config surface churns between minors (see below). |

**Version drift already present in this repo.** `openapi-ts.ts` passes `asClass: true` to the SDK
plugin. In `0.99.0` that option is `@deprecated` (`dist/index.d.mts:4223`): *"Use
`operations: { strategy: 'byTags' }` or `operations: { strategy: 'single' }` instead."* Likewise
`classNameBuilder`, `classStructure`, `instance`, `methodNameBuilder` and `operationId` are all
deprecated in favour of the `operations` object. Since the repo script runs `npx tsx openapi-ts.ts`
against an unpinned dependency, a regeneration months from now can silently change the output
shape. Pin the version and commit the lockfile.

## Open questions / not documented

1. **Does `sdk.client: false` survive the `@hey-api/client-fetch` plugin being dropped entirely?**
   The plugin was kept in the verified run because `sdk.gen.ts` still imports `Client`, `Options`
   and `RequestResult` *types* from `./client`. Whether a config with no client plugin at all
   generates, and what the SDK imports then, was not tested.
2. **How to distinguish a `ZodError` from an HTTP error in `error` without inspecting `response`.**
   The client's `catch` merges three failure kinds into one untyped field, and the source carries
   `// TODO: we probably want to return error and improve types`
   (`out_v2/client/client.gen.ts:214`). The `response.ok` classifier in §3 is inferred from
   reading the implementation, not from documentation, so it is version-fragile.
3. **Whether a `ZodError` from `responseValidator` leaves `data` recoverable.** It does not — the
   result carries `error` and `data: undefined`. Whether "warn on stderr but return the data
   anyway" is achievable at all with `sdk.validator` on was not established; wrapper-side
   `safeParse` sidesteps it and is the reason §2.4 recommends that route.
4. **Whether `parser.patch.schemas` (the per-name form) can target Pipedrive's response schemas.**
   Only the whole-spec `patch.input` form was verified. Pipedrive's v2 response bodies appear to be
   inline under `paths`, with names like `GetDealsResponse` coming from the schema `title`, so the
   per-name form may not reach them. Test before relying on the tidier syntax.
5. **Retry inside a custom `fetch` and `Request` body reuse.** `fetch(request)` consumes a
   `Request` body; retrying requires `request.clone()` before the first attempt. Not documented by
   Hey API. Irrelevant for GET-only traffic today, but worth a note if the gate is ever reused.
6. **`ClientMeta` and the `meta` option.** Generated `Options` carries
   `meta?: keyof ClientMeta extends never ? Record<string, unknown> : ClientMeta`, and `meta`
   reaches `opts` inside the client — a plausible channel for passing per-call budget hints or
   cache keys through to `guardedFetch`. How `ClientMeta` is declared/augmented was not found in
   the docs.
7. **Whether `x-ratelimit-*` / daily-budget response headers are reachable from a response
   interceptor before the body is read.** Reading them there looks correct from the source order
   (interceptors run at line 103-107, body parsing at 147+) but was not exercised against a live
   response.
8. **The Pipedrive v1 job.** The URL is confirmed live —
   `curl -sI https://developers.pipedrive.com/docs/api/v1/openapi.yaml` returns
   `HTTP/2 200`, `content-type: text/yaml`, `content-length: 1781741` (~1.8 MB, roughly 3× the v2
   spec). Generation from it was **not** run, so whether it needs different `patch` corrections,
   or trips over anything the v2 spec did not, is unknown.
9. **`compatibilityVersion` and the installed zod major.** The verified run emitted zod-v4 syntax
   (`z.int()`, `z.iso.date()`, `z.record(z.string(), z.unknown())`) without setting
   `compatibilityVersion`, so it appears to be inferred from the installed `zod`. Set it
   explicitly rather than relying on inference.
