# Map: `pd` — read-only Pipedrive CLI for agent consumption

Label: `wayfinder:map`

## Destination

A **locked design spec** for `pd` — every open design decision argued, decided and written down as `.scratch/pd-cli-design/spec.md` plus ADRs under `docs/adr/` and domain terms in `CONTEXT.md`. No implementation code ships from this map; building `pd` is a separate effort that starts from the spec.

## Notes

**Domain**: a Bun + TypeScript CLI named `pd` that reads data out of the Pipedrive API. Primary consumer is an AI coding agent invoking it as a tool, on no particular harness. Human use is secondary and opt-in. Where agent ergonomics and human ergonomics conflict, the agent wins.

**Safety property, not a scope decision**: the tool is READ-ONLY. GET requests only. No create, update, delete — not behind a flag, not behind a prompt, not ever. An agent must be unable to damage the CRM through this tool no matter what it does. A second safety property: the Pipedrive daily API budget is token-based and shared across the whole company account, so exhausting it breaks colleagues' integrations.

**Locked — do not open decision tickets for these:**

1. Bun + TypeScript, `strict: true`. Argument parsing via `util.parseArgs`, no CLI framework.
2. The Pipedrive client is generated by `@hey-api/openapi-ts` from Pipedrive's OpenAPI v2 spec. Generated output is committed; regeneration is a documented script. Hand-written code wraps the generated client, never edits it.
3. Required libraries, no substitutes: `zod` (runtime validation at every boundary untrusted data enters), `neverthrow` (errors are values; typed error union, not `Error`), `p-limit` (all concurrent HTTP work runs through a limiter; no unbounded `Promise.all`).
4. Harness-agnostic contract: stdout is machine-readable output only, never banners/progress/colour/prose; stderr carries all logging and diagnostics; exit codes 0 success, 1 runtime error, 2 usage error, 3 rate/token budget exhausted; `--pretty` opts into human output; `--no-cache` bypasses cache; `--max-requests <n>` is a hard ceiling that aborts before it is exceeded; `--help` on every subcommand plus a machine-readable command manifest. `AGENTS.md` is the canonical documentation file; harness-specific files point at it.
5. Pagination is complete and correct by default — "all deals" means all of them across as many cursor pages as it takes. Cursor handling is an internal detail the caller never sees.
6. Custom fields must be resolvable to human-readable names and values behind a flag. Raw hashes stay the default so output is stable and diffable.
7. Every HTTP call goes through ONE client module. Rate limiting, retry, concurrency limiting, budget accounting and logging live there and nowhere else.

**Pipedrive realities the design must survive**: token-based shared daily budget; burst limits on a 2-second rolling window with the Search API stricter still; cursor pagination with `limit` max 500; custom fields as 40-character hashes needing per-account resolution, with enum/set fields carrying numeric option ids whose labels also need resolving; an incomplete v1 to v2 migration leaving some resources v1-only.

**Skills every session should consult**: `/grilling` and `/domain-modeling` by default. `/research` for the research tickets. `/prototype` for the prototype tickets. Use `context7` for library and API documentation rather than recalling it.

**Working style**: prototypes are wanted both where the decision hangs on what Pipedrive actually returns, and where it hangs on how output reads to an agent. React to a concrete artifact rather than an abstract argument.

**Grill at the right altitude.** Do not put implementation-technical questions to the user — function signatures, call styles, class versus function, file layout, naming, internal types nobody observes. Grill only on decisions with a consequence the user can see or feel: observable behaviour, the output contract, safety properties, scope, and trade-offs with a user-visible cost. Where an implementation detail must be settled to write the ADR, decide it, state the assumption in the ADR, and give the reasoning — do not ask.

## Decisions so far

<!-- one line per resolved ticket -->

- [Pipedrive rate limiting and the shared daily token budget](issues/01-research-rate-limits-and-token-budget.md) — no header reports remaining daily budget, so accounting must be predictive from a flat per-operation cost table; the 429 is opaque and daily exhaustion is indistinguishable from burst; hammering a 429 earns a Cloudflare 403 with an HTML body that blocks the whole company.
- [Cursor pagination semantics in the Pipedrive v2 API](issues/02-research-cursor-pagination-semantics.md) — cursor lifetime and stability are entirely undocumented and the cursors look like keyset markers rather than snapshot handles; there is no total count anywhere in v2, so a walk's size cannot be estimated before walking it.
- [Custom fields, hash keys and enum option labels](issues/03-research-custom-fields-and-option-labels.md) — `include_option_labels` makes Pipedrive resolve enum and set options for us, but only on some endpoints; field schemas are in v2 except `leadFields` and `noteFields`; duplicate display names are possible and Pipedrive does nothing to disambiguate them.
- [Which resources are v1-only, and what the v2 spec omits](issues/04-research-v1-v2-resource-coverage.md) — three classes, not two: deprecated v1 to never call, a live v1-only set (Leads, Notes, Users, Currencies, ActivityTypes, Filters, changelog) that a second generated client would be needed for, and v2-only. Auth is identical across versions.
- [Pipedrive authentication: API token versus OAuth](issues/05-research-auth-mechanisms.md) — an API token cannot be scoped read-only at all, so with one the read-only property rests solely on `pd`'s own code; OAuth has real `:read` scopes and ~4× the burst headroom, but neither mechanism protects the shared daily budget.
- [What `@hey-api/openapi-ts` can generate and how it can be wrapped](issues/06-research-hey-api-capabilities.md) — `sdk.client: false` removes the ambient client so no call site can bypass the one module, with a custom `fetch` as the choke point; `parser.patch` overrides wrong schemas regeneration-safely.
- [Distributing a Bun CLI to users who may not have Bun](issues/07-research-bun-distribution.md) — the cheap options are a plain npm package (a few hundred KB, but only if `pd` avoids `Bun.*`) or a curl-installed compiled binary (17–28 MB, no signing needed); a browser-downloaded binary requires notarization or it is SIGKILLed.
- [Storing API credentials safely for a local CLI](issues/08-research-secure-credential-storage.md) — `Bun.secrets` is built in, but fails fast in containers and must never be the only path; recommended chain is `--token-file`, `PD_API_TOKEN`, keychain, `0600` file, fail — with named profiles keying both the credential store and the custom-field cache.
- [The error union, exit codes, and machine-readable failure](issues/09-grilling-error-union-and-exit-codes.md) — eleven variants on stdout as a stable `code` field; bounds exit 0 and guards exit 3, with a completeness marker on every list output; an ambiguous 429 stops as `budget_exhausted` because the opposite mistake blocks the whole company. Full detail in [ADR-0001](../../docs/adr/0001-error-model-and-exit-codes.md).

- [Output format for large paginated results](issues/10-prototype-output-format.md) — NDJSON is the only machine format, every line `type`-tagged, and exactly one exclusive trailer whose last line always carries `complete` and `emitted`; `--pretty` is an unstable human table with no machine-readable error object at all. Measured: buffering costs 20 s of silence to first byte and no memory saving. Full detail in [ADR-0002](../../docs/adr/0002-output-format.md).

- [How pagination is bounded, and how partiality is signalled](issues/11-grilling-pagination-bounding.md) — `--limit` counted in records is the only bound and `--max-pages` is cut for exposing page size; `--limit` applies after zod rejection and deduplication, with `skipped` and `duplicates` on every trailer; there is no resumption token, because a cursor of undocumented stability cannot promise one. Full detail in [ADR-0003](../../docs/adr/0003-pagination-bounding-and-partiality.md).

- [How streaming pagination composes with `Result`](issues/12-grilling-streaming-and-result-composition.md) — a paginated read is `AsyncGenerator<Result<Page, PdError>>` that yields only validated, deduplicated, bounded pages, with `bound` riding on the final page; one `NdjsonWriter` owns stdout, the counters and the single trailer, and refuses a second one; `collect` is the specified non-streaming path and emits `emitted: 0` rather than an unsorted prefix. Full detail in [ADR-0004](../../docs/adr/0004-streaming-and-result-composition.md).

- [Cache design: what, where, keyed how, invalidated when](issues/14-grilling-cache-design.md) — a closed list of five near-static resources and no records at all, keyed by a hash of the credential rather than the profile name; TTL 24 h for schemas and 1 h for `users`, overridden by a one-shot refresh on an unrecognised hash; a cache hit does not count against `--max-requests`, which therefore means network requests. Full detail in [ADR-0005](../../docs/adr/0005-cache-design.md).

- [Where zod validation sits, and what a rejected response does](issues/13-grilling-zod-validation-placement.md) — the envelope is validated strictly and fails the whole walk, each record is validated individually and fails only itself; unknown keys are stripped, so a `record` line's shape follows `pd`'s version rather than Pipedrive's release schedule; a first page with no survivors is `invalid_response`, but no later page ever escalates. `warning` lines are deduplicated by cause and gain a `kind`. Full detail in [ADR-0006](../../docs/adr/0006-validation-placement-and-rejection.md).

## Not yet specified

- **Testing strategy against a shared live account.** How `pd` is tested without burning the company's shared daily token budget — recorded fixtures, a replay layer, a sandbox account, or contract tests against the generated types alone. The cache half is now settled by [ADR-0005](../../docs/adr/0005-cache-design.md) — a keyed, version-stamped on-disk store is itself a seam a replay layer could sit behind — so what remains hangs on the client module fixed by the budget guard and concurrency tickets.
- **Field projection.** Whether a `--fields` style projection exists to shrink output against an agent's context budget, and how it interacts with custom field hashes. Hangs on custom field resolution. [ADR-0003](../../docs/adr/0003-pagination-bounding-and-partiality.md) narrows it: `emitted` counts `record` lines, so a projection that drops fields leaves the count untouched — but a projection that could drop a whole record would be a third subtractive filter alongside `skipped` and `duplicates` and would need its own trailer field. [ADR-0006](../../docs/adr/0006-validation-placement-and-rejection.md) narrows it further: unknown keys are stripped, so a projection can only ever drop fields the record schema already admits.
- **Filtering and search surface.** How filters and the stricter-limited Search API are exposed, if at all. Hangs on the command surface.
- **Related-entity expansion.** Whether a deal can pull its person and organisation in one command, and what that does to request count and budget. Hangs on concurrency and budget guard.
- **Manifest schema and its versioning.** The shape of the machine-readable command manifest and how a harness detects a manifest it does not understand. Hangs on the command surface. [ADR-0002](../../docs/adr/0002-output-format.md) removed one part of this: with a single machine format, the manifest declares it once globally rather than per command. [ADR-0004](../../docs/adr/0004-streaming-and-result-composition.md) adds one thing the manifest must express: whether a command streams or collects, since a collected command's time to first byte is its total wall time.
- **Value formatting.** Money, currency and timezone representation in machine output.

## Out of scope

- Any write operation — create, update, delete. A safety property of the design.
- **The v1 API, except the `users` resource.** Leads, notes, currencies, activity types, filters and the changelog are not exposed by `pd`, even though research 04 found them live and v1-only. `users` alone survives, because `owner_id` is otherwise an unresolvable number and [ADR-0005](../../docs/adr/0005-cache-design.md) already reserved it a cache entry. Ruled during [ticket 13](issues/13-grilling-zod-validation-placement.md); [ticket 18](issues/18-grilling-v1-only-resources.md) stays open, rescoped to building that one narrow client.
- Webhooks.
- Multi-tenant support.
- Any UI.
- Implementing `pd`. This map produces the spec; building from it is a separate effort.
