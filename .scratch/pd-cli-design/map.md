# Map: `pd` — read-only Pipedrive CLI for agent consumption

Label: `wayfinder:map`

## Destination

A **locked design spec** for `pd` — every open design decision argued, decided and written down as `.scratch/pd-cli-design/spec.md` plus ADRs under `docs/adr/` and domain terms in `CONTEXT.md`. No implementation code ships from this map; building `pd` is a separate effort that starts from the spec.

## Notes

**Domain**: a Bun + TypeScript CLI named `pd` that reads data out of the Pipedrive API. Primary consumer is an AI coding agent invoking it as a tool, on no particular harness. Human use is secondary and opt-in. Where agent ergonomics and human ergonomics conflict, the agent wins.

**Safety property, not a scope decision**: the tool is READ-ONLY. GET requests only. No create, update, delete — not behind a flag, not behind a prompt, not ever. An agent must be unable to damage the CRM through this tool no matter what it does. A second safety property: the Pipedrive daily API budget is token-based and shared across the whole company account, so exhausting it breaks colleagues' integrations.

**Locked — do not open decision tickets for these:**

1. Bun + TypeScript, `strict: true`. Argument parsing via `util.parseArgs`, no CLI framework.
2. The Pipedrive client is generated by `@hey-api/openapi-ts` from Pipedrive's OpenAPI v2 spec. Generated output is committed; regeneration is a documented script. Hand-written code wraps the generated client, never edits it.
3. Required libraries, no substitutes: `zod` (runtime validation at every boundary untrusted data enters), `neverthrow` (errors are values; typed error union, not `Error`), `p-limit` (all concurrent HTTP work runs through a limiter; no unbounded `Promise.all`).
4. Harness-agnostic contract: stdout is machine-readable output only, never banners/progress/colour/prose; stderr carries all logging and diagnostics; exit codes 0 success, 1 runtime error, 2 usage error, 3 rate/token budget exhausted; `--pretty` opts into human output; `--no-cache` bypasses cache; `--max-requests <n>` is a hard ceiling that aborts before it is exceeded; `--help` on every subcommand plus a machine-readable command manifest. `AGENTS.md` is the canonical documentation file; harness-specific files point at it.
5. Pagination is complete and correct by default — "all deals" means all of them across as many cursor pages as it takes. Cursor handling is an internal detail the caller never sees.
6. Custom fields must be resolvable to human-readable names and values behind a flag. Raw hashes stay the default so output is stable and diffable.
7. Every HTTP call goes through ONE client module. Rate limiting, retry, concurrency limiting, budget accounting and logging live there and nowhere else.

**Pipedrive realities the design must survive**: token-based shared daily budget; burst limits on a 2-second rolling window with the Search API stricter still; cursor pagination with `limit` max 500; custom fields as 40-character hashes needing per-account resolution, with enum/set fields carrying numeric option ids whose labels also need resolving; an incomplete v1 to v2 migration leaving some resources v1-only.

**Skills every session should consult**: `/grilling` and `/domain-modeling` by default. `/research` for the research tickets. `/prototype` for the prototype tickets. Use `context7` for library and API documentation rather than recalling it.

**Working style**: prototypes are wanted both where the decision hangs on what Pipedrive actually returns, and where it hangs on how output reads to an agent. React to a concrete artifact rather than an abstract argument.

**Grill at the right altitude.** Do not put implementation-technical questions to the user — function signatures, call styles, class versus function, file layout, naming, internal types nobody observes. Grill only on decisions with a consequence the user can see or feel: observable behaviour, the output contract, safety properties, scope, and trade-offs with a user-visible cost. Where an implementation detail must be settled to write the ADR, decide it, state the assumption in the ADR, and give the reasoning — do not ask.

## Decisions so far

<!-- one line per resolved ticket -->

- [Pipedrive rate limiting and the shared daily token budget](issues/01-research-rate-limits-and-token-budget.md) — no header reports remaining daily budget, so accounting must be predictive from a flat per-operation cost table; the 429 is opaque and daily exhaustion is indistinguishable from burst; hammering a 429 earns a Cloudflare 403 with an HTML body that blocks the whole company.
- [Cursor pagination semantics in the Pipedrive v2 API](issues/02-research-cursor-pagination-semantics.md) — cursor lifetime and stability are entirely undocumented and the cursors look like keyset markers rather than snapshot handles; there is no total count anywhere in v2, so a walk's size cannot be estimated before walking it.
- [Custom fields, hash keys and enum option labels](issues/03-research-custom-fields-and-option-labels.md) — `include_option_labels` makes Pipedrive resolve enum and set options for us, but only on some endpoints; field schemas are in v2 except `leadFields` and `noteFields`; duplicate display names are possible and Pipedrive does nothing to disambiguate them.
- [Which resources are v1-only, and what the v2 spec omits](issues/04-research-v1-v2-resource-coverage.md) — three classes, not two: deprecated v1 to never call, a live v1-only set (Leads, Notes, Users, Currencies, ActivityTypes, Filters, changelog) that a second generated client would be needed for, and v2-only. Auth is identical across versions.
- [Pipedrive authentication: API token versus OAuth](issues/05-research-auth-mechanisms.md) — an API token cannot be scoped read-only at all, so with one the read-only property rests solely on `pd`'s own code; OAuth has real `:read` scopes and ~4× the burst headroom, but neither mechanism protects the shared daily budget.
- [What `@hey-api/openapi-ts` can generate and how it can be wrapped](issues/06-research-hey-api-capabilities.md) — `sdk.client: false` removes the ambient client so no call site can bypass the one module, with a custom `fetch` as the choke point; `parser.patch` overrides wrong schemas regeneration-safely.
- [Distributing a Bun CLI to users who may not have Bun](issues/07-research-bun-distribution.md) — the cheap options are a plain npm package (a few hundred KB, but only if `pd` avoids `Bun.*`) or a curl-installed compiled binary (17–28 MB, no signing needed); a browser-downloaded binary requires notarization or it is SIGKILLed.
- [Storing API credentials safely for a local CLI](issues/08-research-secure-credential-storage.md) — `Bun.secrets` is built in, but fails fast in containers and must never be the only path; recommended chain is `--token-file`, `PD_API_TOKEN`, keychain, `0600` file, fail — with named profiles keying both the credential store and the custom-field cache.
- [The error union, exit codes, and machine-readable failure](issues/09-grilling-error-union-and-exit-codes.md) — eleven variants on stdout as a stable `code` field; bounds exit 0 and guards exit 3, with a completeness marker on every list output; an ambiguous 429 stops as `budget_exhausted` because the opposite mistake blocks the whole company. Full detail in [ADR-0001](../../docs/adr/0001-error-model-and-exit-codes.md).

- [Output format for large paginated results](issues/10-prototype-output-format.md) — NDJSON is the only machine format, every line `type`-tagged, and exactly one exclusive trailer whose last line always carries `complete` and `emitted`; `--pretty` is an unstable human table with no machine-readable error object at all. Measured: buffering costs 20 s of silence to first byte and no memory saving. Full detail in [ADR-0002](../../docs/adr/0002-output-format.md).

- [How pagination is bounded, and how partiality is signalled](issues/11-grilling-pagination-bounding.md) — `--limit` counted in records is the only bound and `--max-pages` is cut for exposing page size; `--limit` applies after zod rejection and deduplication, with `skipped` and `duplicates` on every trailer; there is no resumption token, because a cursor of undocumented stability cannot promise one. Full detail in [ADR-0003](../../docs/adr/0003-pagination-bounding-and-partiality.md).

- [How streaming pagination composes with `Result`](issues/12-grilling-streaming-and-result-composition.md) — a paginated read is `AsyncGenerator<Result<Page, PdError>>` that yields only validated, deduplicated, bounded pages, with `bound` riding on the final page; one `NdjsonWriter` owns stdout, the counters and the single trailer, and refuses a second one; `collect` is the specified non-streaming path and emits `emitted: 0` rather than an unsorted prefix. Full detail in [ADR-0004](../../docs/adr/0004-streaming-and-result-composition.md).

- [Cache design: what, where, keyed how, invalidated when](issues/14-grilling-cache-design.md) — a closed list of five near-static resources and no records at all, keyed by a hash of the credential rather than the profile name; TTL 24 h for schemas and 1 h for `users`, overridden by a one-shot refresh on an unrecognised hash; a cache hit does not count against `--max-requests`, which therefore means network requests. Full detail in [ADR-0005](../../docs/adr/0005-cache-design.md).

- [Where zod validation sits, and what a rejected response does](issues/13-grilling-zod-validation-placement.md) — the envelope is validated strictly and fails the whole walk, each record is validated individually and fails only itself; unknown keys are stripped, so a `record` line's shape follows `pd`'s version rather than Pipedrive's release schedule; a first page with no survivors is `invalid_response`, but no later page ever escalates. `warning` lines are deduplicated by cause and gain a `kind`. Full detail in [ADR-0006](../../docs/adr/0006-validation-placement-and-rejection.md).

- [The narrow v1 client for `users`](issues/18-grilling-v1-only-resources.md) — the v1 footprint is one generated operation (`GET /users`, verified generable and unpaginated, needing no spec patch because `pd` owns the record schema); `pd users list` and `pd users get` both exist and `get` filters the cached list for zero requests; one `--resolve` flag now covers hashes, option labels and owner ids together, additively, and a failed user fetch degrades to raw ids with one `warning`. Full detail in [ADR-0007](../../docs/adr/0007-the-narrow-v1-users-client.md).

- [Custom field resolution mechanics](issues/15-grilling-custom-field-resolution.md) — resolved values go in a parallel `custom_fields_resolved` block keyed by hash, which dissolves the duplicate-display-name problem instead of solving it, and leaves `custom_fields` byte-identical with and without the flag; `--resolve` covers enum, set, user, person/org relations, monetary and address, and grows ADR-0007's sibling table to seven fields, with relation fetches batched 100 ids per request and capped at 50 requests by default via `--resolve-budget`; every ceiling and every failure degrades to raw ids with one `warning` and `resolved: "partial"` on the trailer, never an abort. Full detail in [ADR-0008](../../docs/adr/0008-resolution-mechanics.md).

- [Command surface, naming, and the machine-readable manifest](issues/19-prototype-command-surface.md) — the grammar is `pd <resource> <verb> [id]` and the first surface is nine resources, with `pd fields list --entity <name>` created and projects, deal children, followers and archived variants left out (so `/projectFields` stays outside the cache); Pipedrive's own nouns win with no aliases and no short flags; `pd manifest` is a subcommand emitting one JSON object — the second exception to the NDJSON rule after `--help` — carrying an integer `manifest_version` that moves only on a breaking change. Found and fixed one inconsistency: ADR-0005's `pd cache info` / `pd cache clear` are grammar exceptions, so the read-only refusal names the absence of writes rather than claiming two verbs. Full detail in [ADR-0009](../../docs/adr/0009-command-surface-and-manifest.md).

- [Budget guard: pre-flight estimation, reactive accounting, or both](issues/16-grilling-budget-guard.md) — `pd` does not guard the shared daily budget and says so, because every input one would need is unreadable and the heaviest single run costs ~1,300 tokens against a smallest-possible pool of 30,000; `--max-requests` is the only quantitative guard and has no default, with ADR-0008 §10's yielding rule promoted so no enrichment can ever trip it. One piece of cross-invocation state survives, and it is a Cloudflare question rather than a budget one: a `blocked` sentinel per credential that refuses with zero requests for 15 minutes, has no override flag, and now survives `pd cache clear` — amending ADR-0005 §7. Ticket 09's retry-cap debt is settled by leaving the cap process-scoped. Full detail in [ADR-0010](../../docs/adr/0010-budget-guard.md).

- [Default concurrency for the p-limit limiter](issues/17-grilling-concurrency-default.md) — concurrency is nearly useless here, because the dominant cursor walk is sequential, so the derived default is a fixed **4** with no flag, no environment variable and no manifest entry; `p-limit` bounds in-flight and the burst limit is a rate, so a rolling 2-second gate sits beside it at half the assumed Lite window (10 req/2 s), raising itself only from an observed `x-ratelimit-limit`. Retry policy settled in numbers: a 429 pauses the whole gate, 3 strikes per run at ≤2 s each ≈ 6 s of stall then `rate_limited`, with 5xx on a separate 3-per-request / 10-per-run budget, and `--max-requests` reserved before dispatch. Confirms ADR-0010 §8's premise; names the consequence that two parallel `pd` processes fit Lite exactly and three do not. Full detail in [ADR-0011](../../docs/adr/0011-concurrency-and-retry.md).

- [Auth mechanism, credential storage, and account selection](issues/20-grilling-auth-and-credential-storage.md) — API token, so the read-only property is openly `pd`'s own code and nothing below it, and ticket 23 inherits the whole mechanism; three tiers (`--token-file`, `PD_API_TOKEN`, a `0600` file `pd` reads but never writes) and never a `--token <value>` flag. Cutting `pd auth login` removed the keychain tier with it, which means no `Bun.*` API is required by any decision so far and ticket 21 keeps the plain-npm-package option; `pd auth status` survives at zero requests and zero writes. Both recorded conflicts closed: exit 1 `auth` beats research 08's exit 2, and profiles are refused because ADR-0005 already keys the cache by credential hash. `GET /users/me` stays out, so ADR-0007 is untouched and the base URL is fixed. Found and corrected ADR-0001's false premise that the token travels as a query parameter. Full detail in [ADR-0012](../../docs/adr/0012-authentication-and-credential-resolution.md).

- [How the read-only property is actually enforced](issues/23-grilling-read-only-enforcement.md) — four layers, every one of them `pd`'s own code: a generation filter that measurably emits 66 GETs and zero writes, a non-GET refusal in the single client's custom `fetch` (not redundant — research 06 §1.5's per-call `fetch`/`baseUrl` overrides route around the filter), an ESLint import ban, and a hard-failing CI gate; a write reaching Pipedrive needs all three of write-exists, CI-missed and guard-bypassed, and nothing outside `pd` enforces any of it. A blocked write is a twelfth ADR-0001 variant, `write_blocked` exit 1, earning its place because the caller must stop using `pd` rather than merely file a bug. The admin-token risk is said, not detected: `pd auth status` gains `credential_is_write_capable` and `warnings`, and no other command carries it. Corrects research 06 §4, which recommends a read-only-scoped token that cannot exist. Full detail in [ADR-0013](../../docs/adr/0013-read-only-enforcement.md).

- [Distribution](issues/21-grilling-distribution.md) — one channel, `@zimple/pd` public on npm as a single bundled `.js` for Node ≥ 20, so the compiled binary and its five-target matrix, signing question and musl split are all declined; the scoped name is forced because `pd`, `pipedrive-cli` and `pd-cli` are taken on the live registry and `pd-cli` already ships a bin named `pd`. Bun becomes the build runtime only, and ADR-0012 §4's `Bun.*`-free freedom is spent by committing to it — an ESLint ban plus CI gate on ADR-0013 §1's machinery. No self-update check ever, because a registry poll is the exact non-Pipedrive HTTP request ADR-0011 and ADR-0013 forbid; semver is defined against the agent-visible contract with `manifest_version` in lockstep. Windows supported with `%LOCALAPPDATA%`/`%APPDATA%` and the NTFS permission gap stated in `pd auth status` warnings. `AGENTS.md` ships and `pd docs` emits it — the third stdout exception. Adds a thirteenth ADR-0001 variant, `unsupported_runtime` exit 2, because npm's `engines` only warns. Full detail in [ADR-0014](../../docs/adr/0014-distribution.md). **Superseded 2026-08-13 by
  [ADR-0021](../../docs/adr/0021-distribution-build-from-source.md)**, on the user's direction that
  `pd` be built from a clone with `bun build --compile`: the npm channel, the Node target, the ES2020
  prelude, `unsupported_runtime` and the `Bun.*` ban are all withdrawn; the semver contract, the
  Windows mapping, the no-self-update refusal and `pd docs` survive. Notarization is not needed
  because a locally built binary carries no quarantine xattr, and the `.env`-autoload footgun ADR-0014
  declared dead returns and is closed by two mandatory build flags. This repository becomes public and
  the fixtures move to a private one of their own.

- [What stderr carries, and how a long run reports progress](issues/24-grilling-stderr-diagnostics.md) — default stderr is exactly two things and neither is progress (ADR-0001's error line, ADR-0003's per-10,000-record warning), safe because **in machine mode nothing on stderr is the sole carrier of any fact** (`--pretty` excepted, and its reader is a human at the terminal); progress is TTY-gated on stderr's own descriptor, which accepts environment-dependent behaviour precisely because stderr is declared not a contract — prose only, no JSON, no `--log-format`, so if telemetry is ever wanted the answer is "there is none". One `\r`-rewriting status line at ~1 Hz plus permanent anomaly lines for ADR-0011's gate pauses and self-raising ceiling, closing that ADR's explicit handoff by making the gate visible without making it settable. `--verbose` is the eighth global flag and the only surface addition — no `-v`, no `--quiet`, no `PD_LOG`, and it never changes a byte of stdout. Redaction is allowlist-based on both query values and headers, so a future parameter leaks nothing by default; response bodies never logged. No new error variant and no exit-code change. Full detail in [ADR-0015](../../docs/adr/0015-stderr-and-run-diagnostics.md).

- [Field projection: shrinking output against an agent's context budget](issues/25-grilling-field-projection.md) — `--fields` exists as the ninth global flag (the `jq` counter-argument fails because a harness capturing stdout has already spent the tokens), with `id` always emitted; the grammar is bare top-level names plus `custom_fields.<hash>` and never a display name. One rule settles both of ADR-0008's second-key problems — **a resolution artifact rides with its raw field and is never selectable alone** — which buys the invariant that the legal selector set does not depend on `--resolve`. Projection removes fields, never records, so the trailer is untouched and filtering stays ticket 26's. Unknown name is exit 2 offline (ADR-0006 makes the schema `pd`'s own); an unmatched hash is one `warning`. **Corrects the ticket's own premise**: `include_fields` is additive and cannot trim, so it is never sent and its namespaces are outside `pd`'s schema — the real push-down is `custom_fields`, max 15 keys on four resources, and it is contract-invisible because output is byte-identical either way. Manifest gains a per-command selectable-field list, because an agent that cannot enumerate fields must run unprojected to learn them. Full detail in [ADR-0016](../../docs/adr/0016-field-projection.md).

- [The search surface, and what the stricter search rate limit costs](issues/26-grilling-search-surface.md) — a search hit is **not** a record (truncated `item` + `result_score`), which kills `list --search` outright and forces a third verb: `pd <resource> search <term>` on four resources plus a tenth resource `items` with neither `list` nor `get`, amending ADR-0009 §1 and §3 while keeping its exception list closed. `item_types` is pinned to the four in-scope types so `itemSearch` cannot re-admit leads; `/leads/search` and `/itemSearch/field` get no command. Four silent collisions found and fixed — `item.type` against the line kind, the hit's `string[]` `custom_fields` against ADR-0008's hash object, the endpoints' `fields` parameter against ADR-0016's `--fields` (so the flag is `--search-in`), and `filter_id` silently voiding `ids`. Search shares `--max-requests` with no ceiling of its own, because resolution's requests were implicit and search's are asked for; ADR-0011's double-spend reading is confirmed. The filtering half is settled too: fifteen command-scoped filter flags off the v2 list vocabulary, with `--updated-since` the honest incremental read ADR-0003 refused to fake. Full detail in [ADR-0017](../../docs/adr/0017-search-and-list-filtering.md).

- [Related-entity expansion: pulling the whole related record](issues/27-grilling-related-entity-expansion.md) — there is no expansion and `--resolve` stays legibility rather than data; the whole related record is a **second command**, `pd deals list --fields org_id` then `pd organizations list --ids 7,9,11`, shipped in `AGENTS.md` as a recipe. The fact that decided it is that `ids` is a parameter on the *same operation* as the unfiltered list, so the second command issues exactly the request an in-run expansion would have issued — **request cost against the shared budget is identical either way**, which removes expansion's only real argument. The close rival, deduplicated sibling `record` lines, is rejected on the five contract questions it forces (`emitted` arithmetic, its own ceiling, page-1-vs-page-40 partiality, `--fields` across two shapes, ADR-0016 §2's grammar reaching inside a nested block) — every one answered by never asking it. Found and closed one real gap: ADR-0017 §7's `--ids` ignored the API's 100-id ceiling, so it now chunks client-side and invisibly. `search_for_related_items` refused — its `related_items` are truncated hits, not records. Net surface: one `warning` kind, `unmatched_ids`; no flag, no line type, no trailer field, no error variant, and `manifest_version` does not move. Full detail in [ADR-0018](../../docs/adr/0018-related-entity-expansion.md).

- [Testing strategy against a shared live account](issues/28-grilling-testing-strategy.md) — three layers with their blind spots named, and the replay layer sits at `guardedFetch` *below* ADR-0013's refusal, so no test can test past the read-only property; zero requests per `bun test` is mechanical rather than disciplined, because the default gate has a transport that throws. One injected clock covers six timing behaviours and is ruled a seam, not complexity — the retry test alone costs ~6 s of real time and the TTLs are untestable without it. No test-only flag or environment variable exists at all: isolation runs on the `XDG_*` and Windows paths already defined, which is how a test places the `blocked` sentinel without making it settable by an agent. Cache reuse refused — the two stores are permitted to fail in opposite directions. Suite under Bun plus a short smoke leg on the built artifact — *per ADR-0021 §8 that is a **binary** smoke leg on Linux and Windows, and what it alone can assert is the version stamp, the embedded `AGENTS.md`, the absence of an embedded fixture and the CWD `.env` refusal; the Node legs and `unsupported_runtime` are gone*. **User's two decisions**: a hand-invoked live suite against the real company account, never CI, never scheduled, whose output is a re-recording and a git diff rather than a pass/fail — and which never tests a retry, a 429 or the Cloudflare block, permanently; and recorded fixtures keep real CRM data verbatim, which makes the repository's privacy a load-bearing design property — **amended by ADR-0021 §9: the fixtures leave for a private repository and the code repository becomes public, which is free only until the first fixture is recorded** — forces the artifact to embed no fixture, and leaves credential stripping mechanical regardless. Net agent-visible surface: zero. Full detail in [ADR-0019](../../docs/adr/0019-testing-strategy.md).

- [Value formatting: money, currency and time in machine output](issues/29-grilling-value-formatting.md) — money is a JSON number with `currency` as a flat sibling, because folding the pair into an object would create a block ADR-0016 §2's grammar cannot name; time passes through byte-for-byte and is never parsed, since the v2 spec declares those fields as bare `type: string` with no `format` and a normalising `pd` would be the component that is silently wrong about time; the account timezone is never read and date-only fields are declared account-local wall clock. **User's decision**: a field with no value is an absent key, so the agent's context budget beats a fixed record shape — with `[]`, `""` and `0` staying values, `custom_fields` exempt under ADR-0008 §1, and `--fields` on an empty field yielding a shorter line rather than a warning. **Kills the ticket's own premise**: `weighted_value` is not a v2 field at all. **Found and corrected**: one nested block does exist, `products.prices`, falsifying ADR-0016 §2's stated premise and ADR-0018's Consequences claim — both decisions survive, because `prices` is selectable only whole. Net agent-visible surface: zero. Full detail in [ADR-0020](../../docs/adr/0020-value-formatting-and-absence.md).

## Out of scope

- Any write operation — create, update, delete. A safety property of the design.
- **The v1 API, except the `users` resource.** Leads, notes, currencies, activity types, filters and the changelog are not exposed by `pd`, even though research 04 found them live and v1-only. `users` alone survives, because `owner_id` is otherwise an unresolvable number and [ADR-0005](../../docs/adr/0005-cache-design.md) already reserved it a cache entry. Ruled during [ticket 13](issues/13-grilling-zod-validation-placement.md); [ADR-0007](../../docs/adr/0007-the-narrow-v1-users-client.md) then cut the survivor down to a single generated operation, `GET /users`, and additionally excluded the seven other `users` endpoints the spec offers — `users/{id}`, `users/me`, `users/find`, followers, permissions, role assignments and role settings.
- **The v2 `include_fields` namespaces.** Activity and file and note counts, follower and participant counts, mail timestamps, `smart_bcc_email`, `source_lead_id`, `ui_visibility` — none of them are in `pd`'s record schema, so none are emitted and none are selectable. Ruled during [ticket 25](issues/25-grilling-field-projection.md): the parameter is *additive* rather than subtractive, so requesting a namespace costs response size on every record of a walk to serve a question `pd` was not built to answer. Adding one later is additive under [ADR-0014](../../docs/adr/0014-distribution.md)'s semver rule and needs no `manifest_version` bump, so this closes nothing off permanently — it just refuses to pay for it by default.
- Webhooks.
- Multi-tenant support.
- Any UI.
- Implementing `pd`. This map produces the spec; building from it is a separate effort.
